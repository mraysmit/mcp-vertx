## Detailed implementation progress

### 1. Project coding principles

The project guidance in [coding-principles.md](coding-principles.md) now covers:

- Vert.x 5 event-loop ownership and context affinity.
- Deliberate use of `executeBlocking` for bounded blocking work.
- Correct use of `compose`, `map`, `recover`, `transform`, `eventually`, and
  `Future.timeout`.
- The distinction between timeout signaling and cancellation of underlying work.
- Verticle lifecycle, timer cleanup, readiness, and fire-and-forget failures.
- Security-sensitive Vert.x Web handler ordering.
- Separation of HTTP transport, JSON-RPC, MCP metadata, and tool-execution errors.
- Bounded request bodies, response envelopes, schema complexity, concurrency,
  execution time, and cleanup.
- Tool providers as untrusted extension boundaries.
- Real-HTTP tests, deterministic asynchronous assertions, packaged-application
  checks, and verification that tests actually executed.

These rules are now phrased for `mcp-vertx` rather than PeeGeeQ and explicitly
target Java 25, Vert.x 5.1.x, and the MCP revision declared by the server.

### 2. MCP request metadata and protocol handling

[McpServerVerticle.java](../src/main/java/dev/mars/mcp/McpServerVerticle.java)
was updated to enforce a clearer failure taxonomy:

- A missing or blank `MCP-Protocol-Version` HTTP header is a protocol-version
  failure.
- A missing/non-object request `_meta`, or a missing body protocol version, is
  invalid request metadata.
- Header/body version mismatch is a protocol-version failure.
- A matching but unsupported version is reported separately.
- Known client capabilities must have object-shaped values.
- Nested `sampling.context`, `sampling.tools`, `elicitation.form`, and
  `elicitation.url` capabilities are also shape-checked.
- Retried tool calls validate `inputResponses`, request IDs, method-specific
  response objects, and `requestState` before provider invocation. The response
  objects deliberately do not require a top-level `resultType`; elicitation,
  sampling, and roots results have different standard shapes.

The changes preserve the distinction between HTTP status and JSON-RPC/MCP error
codes instead of collapsing all failures into a generic request error.

### 3. Multi-round-trip tool results

Multi-round-trip handling was aligned with the current MCP shape:

- Added [McpInputRequest.java](../src/main/java/dev/mars/mcp/tool/McpInputRequest.java)
  as a typed representation of a server-initiated request.
- Supported methods are `elicitation/create`, `sampling/createMessage`, and
  `roots/list`.
- `inputRequests` is keyed by server-assigned request ID; the request method and
  parameters are carried in each value.
- Required client capabilities are derived from each request value's `method`,
  rather than from its map key.
- Nested sampling and elicitation capabilities are enforced where required.
- `InputRequiredToolResult.stateOnly(...)` supports load shedding and other
  flows that return state without creating a new input request.
- Required-capability error details are emitted as structured capability objects.

See [InputRequiredToolResult.java](../src/main/java/dev/mars/mcp/tool/InputRequiredToolResult.java)
and the usage example in [README.md](../README.md).

### 4. Structured JSON results and schema validation

`CompleteToolResult` is no longer limited to object-shaped structured content.
It now supports:

- JSON objects and arrays.
- Strings, booleans, and finite numbers.
- An explicit JSON `null` through `CompleteToolResult.structuredNull()`.
- Defensive copies on construction, access, validation, and serialization.
- A compatibility accessor for callers that still expect object-valued content.

[McpJsonValues.java](../src/main/java/dev/mars/mcp/tool/McpJsonValues.java)
centralizes detached JSON-value copying and rejects unsupported Java values,
non-string map keys, and non-finite floating-point numbers.

[ToolSchemaValidator.java](../src/main/java/dev/mars/mcp/tool/ToolSchemaValidator.java)
now validates arbitrary structured JSON values against advertised output schemas,
not only `JsonObject` instances.

### 5. Tool-provider boundary hardening

Provider-produced data is treated as untrusted even though it originates inside
the JVM. [McpWireValidator.java](../src/main/java/dev/mars/mcp/tool/McpWireValidator.java)
now validates provider-controlled wire structures before serialization:

- Standard text, image, audio, resource-link, and embedded-resource blocks.
- Required fields, field types, absolute resource URIs, and exactly one of
  embedded-resource `text` or `blob`.
- Content annotations, audience roles, priority range, and last-modified values.
- Tool icons, allowed URI schemes, sizes, MIME types, and light/dark themes.
- Standard tool annotation value types.
- Metadata key safety and JSON-compatible values.
- Extension content types while retaining a valid, non-blank discriminator.

The public result constructors now normalize malformed provider values into the
expected `IllegalArgumentException` boundary rather than leaking Vert.x
`JsonObject.copy()` implementation exceptions.

### 6. HTTP media and mirrored-header validation

HTTP transport parsing was tightened:

- `Content-Type` is parsed as a media type and must be `application/json`.
- `Accept` is parsed by comma-separated media range rather than substring match.
- Both `application/json` and `text/event-stream` must be explicitly acceptable.
- `q=0`, invalid quality parameters, and lookalike media types are rejected.
- Plain mirrored parameter headers must contain visible ASCII without leading or
  trailing whitespace.
- Existing Base64 header decoding remains available for encoded values.

This avoids accepting values such as media-type lookalikes merely because they
contain a required token as a substring.

### 7. Logging and diagnostics

Logging was migrated from `java.util.logging` to SLF4J 2 and Logback:

- Runtime configuration: [logback.xml](../src/main/resources/logback.xml).
- Test configuration: [logback-test.xml](../src/test/resources/logback-test.xml).
- Vert.x defaults to `SLF4JLogDelegateFactory` when the operator has not selected
  another delegate.
- An explicitly configured Vert.x logging delegate is preserved.
- INFO records lifecycle, safe HTTP outcomes, tool milestones, limits, and
  classified failures.
- DEBUG records routing, validation, concurrency, response sizes, timing, and
  test execution context.
- The shared JUnit extension logs class/test start, result, duration, unique ID,
  tags, and thread.
- Integration-test helpers log deployment and HTTP request/response status flow.

Sensitive data is intentionally excluded: authorization values, tool arguments,
mirrored parameter values, query strings, and tool-result bodies are not logged.
Log levels can be adjusted using the environment variables documented in the
[README](../README.md#logging).

### 8. Test and coverage improvements

The test suite was expanded across both protocol and Java API boundaries.
Notable additions cover:

- Missing protocol headers versus malformed request metadata.
- Malformed nested client capabilities.
- Correct multi-round-trip request IDs, methods, capability derivation, state-only
  results, and retry response validation.
- `Accept` lookalikes, invalid quality values, and `q=0`.
- Array, primitive, object, and explicit-null structured results.
- Generic output-schema validation.
- JSON defensive copying, invalid map keys, unsupported values, and non-finite
  numbers.
- Provider content blocks, resources, annotations, metadata, icons, and URIs.
- Logging delegate defaults and explicit-configuration preservation.

The integration suite continues to exercise real Vert.x HTTP servers rather
than bypassing routing and transport behavior.

## Important design decisions

1. The server targets stateless Streamable HTTP at `POST /mcp`; legacy session
   initialization and HTTP+SSE endpoints are intentionally not restored.
2. Tool providers are extension boundaries and their advertised/runtime wire data
   is validated before it reaches a client.
3. Schema validation remains off the event loop through bounded
   `executeBlocking` use.
4. A Vert.x `Future.timeout` is not treated as cancellation; cooperative provider
   cancellation remains a separate responsibility.
5. Structured content follows the complete JSON data model rather than assuming
   every schema has an object root.
6. MCP multi-round-trip capability checks follow the request method inside each
   request value, with map keys reserved for request IDs.
7. Logging prioritizes operational context while excluding payloads and secrets.

## Remaining work and known limitations

### Standard MCP OAuth interoperability

The opt-in OAuth resource-server layer is now implemented separately from the
private `MCP_AUTH_TOKEN`/`mcp.authToken` mode. It provides:

- RFC 9728 Protected Resource Metadata at the well-known path derived from the
  canonical MCP resource URI.
- RFC 8414 authorization-server discovery with OpenID Connect Discovery fallback.
- Vert.x OAuth2 JWKS retrieval and signed JWT validation.
- Exact configured issuer and RFC 8707 audience validation, expiration checks,
  configurable clock skew, and required-scope enforcement.
- Bearer challenges containing `resource_metadata`, with `invalid_token` on 401
  and `insufficient_scope` plus the required scope on 403.
- Startup rejection for insecure public resource URIs, non-loopback HTTP issuers,
  discovery issuer mismatch, and simultaneous fixed-token/OAuth configuration.
- Real HTTP integration coverage using a purpose-built authorization server and
  real RSA-signed access tokens; no mocking framework is used.

Remaining authorization work is deployment/client-side rather than basic token
validation. The local stack now exercises issuer-bound pre-registration with an
official MCP client; the deployment must still select its production strategy
(Client ID Metadata Documents or explicit pre-registration), production
authorization service, credentials, and trust boundary. RFC 9207 applies to
authorization responses handled by the client and authorization server, not to
this resource server's bearer-token endpoint.

### Production-style OAuth reference integration

The repository now contains a reproducible local reference deployment under
`integration/oauth/`:

- Keycloak `26.6.3`, pinned explicitly, imports a test realm at startup.
- A pre-registered confidential client uses client credentials for automated
  resource-server verification, and a public native client uses authorization
  code with mandatory S256 PKCE for interactive-client verification.
- An optional `mcp:read` client scope populates the access-token scope claim.
- The runner generates a Keycloak realm whose audience mapper emits the exact
  canonical resource URI. TLS defaults to `https://localhost:18443/mcp` and is
  configurable with `-HttpsPort`, avoiding collisions with unrelated stacks.
- Caddy `2.11.4-alpine`, also pinned explicitly, terminates HTTPS using its local
  CA and proxies to the OAuth-enabled shaded JAR.
- `scripts/run-oauth-integration.ps1` builds the JAR, starts and cleans up the
  stack, obtains scoped and unscoped real tokens, validates JWT claims, performs
  authenticated MCP discovery through TLS, verifies 401/403 challenges,
  completes authorization code + S256 PKCE with state/RFC 9207 issuer checks,
  and runs official MCP Inspector `2.2.0` `tools/list` with the PKCE token.

The finalized successful 2026-08-16 Inspector/PKCE run is recorded in
`logs/oauth-integration-20260816-142808.log`, with MCP diagnostics in
`logs/oauth-integration-server-20260816-142808.log` and Keycloak/Caddy output in
`logs/oauth-integration-stack-20260816-142808.log`. The integration deliberately
uses committed local-test-only credentials and Keycloak development mode; these
are fixtures, not deployment defaults.

This closes the reproducible token-issuance, PKCE, official-client, and
TLS-boundary validation gaps. The Inspector exposed two interoperability gaps
that are now regression tested: standard `initialize` does not carry the
post-negotiation protocol header, and Inspector `2.2.0` negotiates stable MCP
`2025-11-25`. Standard traffic supports that version while the namespaced
extended profile remains strict on `2026-07-28`. A real deployment must still
select its authorization service, configure production credentials and HTTPS
trust, and choose Client ID Metadata Documents or issuer-bound pre-registration.

## 2026-08-17 A2A v1.0 sibling transport

The runtime now has an opt-in A2A v1.0 HTTP+JSON transport under
`dev.mars.a2a`. It intentionally sits beside MCP on an independent listener:
MCP remains on port 3001, while A2A defaults to loopback port 3002 and base
path `/a2a`. The wire codec uses the official A2A Java SDK v1.1.0.Final models,
generated v1 protobuf messages, and ProtoJSON rather than maintaining local
copies of the protocol schema.

Completed with test-first RED/GREEN evidence under `logs/`:

- Agent Card discovery and v1 version selection
- stateless message send
- task persistence, retrieval, filtered cursor listing, and cancellation
- ordered SSE message streaming and task subscription with backpressure
- status/artifact update application and terminal-state immutability
- public-bind protection and fixed bearer authentication for operations
- opt-in `ServiceLoader<A2aAgent>` startup with exactly-one-provider validation

`docs/a2a.md` documents the provider SPI, route table, security posture, and
known limits. The default task store remains process-local. Push notification
configuration, authenticated extended Agent Cards, and JSON-RPC/gRPC bindings
remain explicit follow-up work.

Verification completed on 2026-08-17:

- `scripts/verify-packaging.ps1`: repeat packaging and executable-JAR structure
  passed with A2A classes present in the shaded artifact.
